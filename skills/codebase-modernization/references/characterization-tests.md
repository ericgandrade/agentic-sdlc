# Characterization tests (`CHAR-n`)

Load at Step 6. Contract: `../../agentic-sdlc/references/brownfield.md` §1. Owners: Test Engineer (designs and writes CHAR tests at the base commit; may read the code, unlike acceptance-test design) and Developer (pins before each change in Build, per the `test-driven-development` brownfield variant).

A characterization test records what the code does today — not what it should do. It is a safety net for the change, and a precise statement of current behaviour that ACs can refer to ("today 10.00, pinned by CHAR-3").

## 1. Selecting targets

1. List the functions, endpoints, jobs and queries the plan's `## Impact` will modify.
2. Run coverage on those files at the base commit. A modified line executed by no test is a target.
3. Add observable outputs consumers rely on (Hyrum's Law): formats, ordering, status codes, error messages, rounding, time zones — for components with > 5 consumers in the inventory.
4. Stop at the plan's footprint. Coverage of untouched code is not a goal of this step.

Target met: 100% of the lines the plan modifies are executed by ≥ 1 existing or `CHAR-n` test. A line with no reachable seam → missing-seam finding (`NEEDS_CONTEXT` to the Planner with the line cited).

## 2. Seams

A seam is a place where behaviour can be observed or substituted without editing the code under test. Prefer, in order:

| Seam | Use when | Example |
|---|---|---|
| Public entry point | The behaviour is reachable from an endpoint, CLI command or exported function | Call `POST /invoices/preview` with a synthetic body |
| Object seam | Collaborators are passed in or created by an overridable factory | Pass a fake clock to `InvoiceService(clock)` |
| Module/link seam | The language resolves dependencies at load time | Jest module mock, Python `monkeypatch` of an imported name, a test-only build target |
| Configuration seam | Behaviour switches on config or env | Point the DB URL at a disposable local database |

No seam → add the smallest one in its own **behaviour-neutral commit** before the CHAR tests: add a parameter with the old value as default, inject a dependency through the constructor, or extract a pure function the old code still calls. The commit message says `refactor: add seam for CHAR-n (no behaviour change)`; the existing suite stays green across it.

Further techniques for code that cannot take a seam yet: *sprout* (write new logic in a new tested function and call it from the old code) and *wrap* (put a tested wrapper around the old call). Both add tested code without characterizing the old code; they do not replace CHAR tests for lines the plan modifies.

## 3. Writing the tests

**Name.** ID first, then behaviour: `CHAR-3 legacy rounding keeps half-even`. Known bug: `CHAR-7 discount applied twice for bundles (pins bug #212)`. The ID makes `git grep CHAR-3` find the test, its register row and every commit that touched it.

**Number.** Unique in the repository, never reused:

```bash
git grep -hoE "CHAR-[0-9]+" | sort -t- -k2 -n | tail -1   # highest existing; next = +1
```

**Expected values.** Run the code, record what it returns. Do not "fix" the expectation; a wrong-looking value is pinned and, if it is a bug, an issue is opened and the test name carries `(pins bug #n)`.

**Inputs.** Synthetic only — generated by the test or written by hand to look like the domain. Never copied from production, support tickets, logs or database dumps; never real names, emails, phone numbers, account numbers or health data.

**Determinism.** Fix the clock, seed random generators, sort unordered collections before comparing, and scrub volatile fields (see §4). A CHAR test that flakes is fixed before the change starts; quarantining it is a weakened check.

**Granularity.** One behaviour per test. For wide surfaces (report generators, serializers), use a golden master (§4) instead of hundreds of asserts.

## 4. Golden master and approval files

For outputs too large to assert field by field:

1. Generate a fixed set of synthetic inputs (seeded generator; record the seed). Cover boundaries: empty, one, many; zero, negative, maximum; each enum value; each branch the coverage report shows.
2. Run the legacy code; write each output to an approval file next to the test (`__approved__/CHAR-12.invoice-pdf.approved.txt`).
3. Scrub volatile fields with named scrubbers before writing and before comparing: `scrubTimestamps` (ISO dates → `<date>`), `scrubIds` (UUIDs → `<id-1>`, `<id-2>` by first appearance), `scrubHostnames`. Each scrubber is listed in the test file; a scrubber that hides a behaviour the plan changes is not allowed.
4. The test compares fresh output against the approved file; a difference fails with a diff.
5. **First approval is reviewed by the Test Engineer**, not the Developer of the change: approved files define truth, so the person changing the code does not approve them.

Updating an approved file follows the change rule (§6): only in the commit carrying the AC that changes that output.

## 5. Proving a CHAR test can fail

CHAR tests pass on their first run — that is their purpose — so the TDD "red first" proof does not apply. Instead, per test:

1. Mutate the pinned line once (flip a comparison, change a rounding mode, return a constant, remove a branch).
2. Run the single test; paste the failing output in the PR Verification section.
3. Revert the mutation; confirm green.

A test that stays green under every reasonable mutation of the pinned line pins nothing — rewrite it. A mutation-testing tool on the touched file (`stryker`, `mutmut`, `pitest`) may replace the manual step; paste its surviving-mutant count for the pinned lines.

## 6. Register and change rule

Register: the `## CHAR register` table in `specs/NNN-slug/current-state.md` (Quick path: the PR body).

| ID | Behaviour pinned | Citation | Pins bug | Protects | Status |
|---|---|---|---|---|---|
| CHAR-3 | Invoice total rounds half-even to 2 dp | `billing/legacy/Invoice.php:212 @ 4f1c2a9b0d3e` | — | AC-1 (unchanged totals) | superseded by AC-2 |
| CHAR-7 | Bundle discount applied twice | `billing/legacy/Discount.php:88 @ 4f1c2a9b0d3e` | #212 | — | active |

Statuses: `active` · `superseded by AC-n` (assertion changed in the AC-n commit) · `retired with AC-n` (behaviour removed by an AC, test deleted in that commit).

A CHAR test changes (assertion, approved file, scrubber, skip, deletion) only in the commit that carries the AC or spec revision changing that behaviour: `Refs: Tn AC-n`, reason in the commit body, register row updated in the same PR. Any other change weakens a check — Critical finding (`../../agentic-sdlc/references/tdd.md` rule 6). Changing untested code without CHAR tests or a ruled missing-seam finding is an Important finding.

## 7. Task shape

- Default: the CHAR commit is the first commit of the task that changes the code — pin (green) → AC-n red → green.
- Standalone pinning task (wide surface, or pins shared by several tasks): at most 1 per plan, lists the ACs it enables, closes with `node ../agentic-sdlc/scripts/run-ledger.mjs task --run <id> --task Tn --state done --no-red "characterization: CHAR-a..b"` (path relative to the skill folder; from the repository root use `skills/agentic-sdlc/scripts/run-ledger.mjs`).
- The PR lists CHAR tests in their own Verification rows, separate from acceptance tests.
